# 决策：把 prompt 增量从 `return str` 升级为 `PromptContext` + `<context>` 外裹

日期：2026-05-24
作者：DJJ
对应 spec：`docs/superpowers/specs/2026-05-24-yapi-v2.2-design.md`
落地 commit：`441b839` / `e72d468` / `90c755d` / `03a3229` / `659da4c`

## 背景

v2.1 把 yapi 收拢为 "FastAPI superset + 显式 prompt 入口"，但有两个 v2 留下的设计妥协一直没修：

1. **`return` 值双重语义**：用户函数返回注解是 `WishOut`（结果模型），实际允许返回 `None | str`（prompt 段）。靠 handler 内的类型守卫强行兜住，但 `return` 同时承担"结果"与"prompt 段"是个语义错位。
2. **没有"结构化片段"通道**：越来越多应用需要把用户档案 / 订单 / 商品快照等塞进 system prompt。v2.1 下唯一通道是 `return "string"`，开发者被迫自己 `json.dumps` 再拼 `\n\n`。

同时，v0 与 v2.1 草稿期讨论过的"state 集成"方向（`state_storage=` / `state_dependencies=` / `Annotated[T, FromState(...)]`）一直没进 v2.2，这是有意的。

## 决策

把"塞 prompt 增量"做大、做正：

1. **新增 `PromptContext` 注入对象**：声明 `ctx: PromptContext` 参数，yapi 在请求期自动新建实例。三方法 `add / add_kv / add_section` append-only。
2. **`<context>...</context>` XML 外裹**：所有 ctx 片段 + `return str` 动态段统一裹一层 XML，作为 system prompt 最后一段；无任何段时整段省略。
3. **不集成 state 存储**：state 这件事不归 yapi 管。Redis / Mongo / SQL 等客户端用 FastAPI 原生 `Depends` 拿；过滤、转换、决定哪些事实进 prompt 由开发者写。

## 为什么这么做

### 为什么是注入对象而不是 `return List[str]`

- **prompt 增量是 side effect，不是 return value**：函数 `return` 应该承载"函数结果"语义。借鉴 FastAPI `BackgroundTasks` 与 Starlette `Request` 的设计取向——副作用通道走"被注入对象 + 多次调用"。
- **支持结构化输入**：`ctx.add(value)` 接受任意类型，yapi 按 `_format_value` 规则转字符串。开发者不必为了塞 prompt 而手动 `json.dumps`。
- **保留 `return str` 兼容**：v2.1 的 `return "hint"` 风格仍然合法——handler 把它当作 ctx 的最后一段塞进同一个 `<context>` 段。无需破坏老路由。

### 为什么外裹 `<context>` XML

- **让 LLM 区分"上下文事实"与"系统指令"**：system prompt 含 default prefix、response_doc、function_doc 三段静态内容 + 动态片段。外裹一层标签让模型清楚哪部分是"事实片段"。
- **段间用 `\n\n` 不够**：v2.1 把动态 prompt 跟 docstring 一样 `\n\n` 拼，LLM 无法区分。XML 标签是行业惯例（Anthropic、OpenAI 文档都推荐）。
- **空段省略**：无任何 ctx add 且 `return` 也无非空 str 时整段不输出——避免空 token 浪费，让 v2.2 路由在"无动态段"场景下 prompt 形态与 v2.1 完全一致。

### 为什么不集成 state

考虑过的方向（都没进 v2.2）：

| 方案 | 为什么不做 |
|---|---|
| 内置 `StateStore` Protocol（Redis / Mongo / SQL 抽象） | 存储侧客户端用 FastAPI 原生 `Depends(...)` 拿就好，yapi 再造一层是无用的中间层。 |
| `Annotated[T, FromState(...)]` marker | ID 解析（user_id？session_id？复合 key？）每个项目都不一样，yapi 内置 callable 最终只会变成"开发者绕开它写 Depends"。 |
| 装饰器 `state_storage=` / `state_dependencies=` | v0 spec 的方向，与 FastAPI Depends 重叠 90%。 |

立场：**把"塞 prompt"这条通道做大，state 这件事完全留给开发者**。yapi 在通道上只做两件事：注入 `PromptContext`、把片段拼接 + 外裹 + 加到 system prompt。

`examples/state_via_depends.py` 演示了完整的"Depends 拿 store + ctx.add_section 塞 prompt"组合——这正是"yapi 不做 state 集成"靠 FastAPI 自然能力解决的样例。

## 替代方案与权衡

### 1. `Annotated[PromptContext, ...]` 也允许（rejected）

考虑过让 `Annotated[PromptContext, Body()]` 也合法，把 ctx 当成"特殊的 Body 标记"。**拒绝**：
- 与"ctx 是 yapi 自动注入、FastAPI 不感知"冲突。
- FastAPI marker 暗示有外部输入，但 ctx 是请求局部新建的空容器，没有输入语义。
- 装饰期报错比静默忽略 marker 更显性。

### 2. `ctx.clear / pop / extend`（rejected）

考虑过加 mutation API。**拒绝**：
- append-only 简化了"段序与调用序一致"不变量。
- 条件添加用 Python 原生 `if` 同样自然：`if profile.vip: ctx.add(...)`。
- YAGNI——目前没有真实场景需要删除已添加的段。

### 3. 多个 `<context>` 块（rejected）

考虑过 `<user_context>` / `<item_context>` 分离。**拒绝**：
- 一个路由一个 `<context>` 够用，里面用 `add_section(name, ...)` 区分子段。
- 多块外裹会让 prompt 结构变复杂，对 LLM 不一定更友好（待实测）。

### 4. RunnerContext 加 `prompt_segments` 字段（rejected）

考虑过让 runner 看到 segment 级粒度。**拒绝**：
- 90% 的 runner 只 care 拼好的 `prompt: str`。
- 想看 segment 的 runner 自行 parse `<context>` 即可。
- YAGNI 推迟到未来有真实需求时再加。

## 实施结果

- 7 个 commit 一次性落库（5 个 feat/test + uv.lock 同步 + plan 文档）。
- 79 个测试全过（68 v2.1 既有 + 11 新增）。
- 版本 `0.2.0 → 0.3.0`（按 v2.2 spec §9.3：0.x 期允许 MINOR bump 引入小破坏点）。
- 唯一 user-visible 破坏点：v2.1 路由 `return "hint"` 现在裹进 `<context>`，substring 断言仍成立，绝大多数 prompt 对 XML 鲁棒。

## 后续 / 待回头看

- 是否需要 segment 级 runner 接口（`RunnerContext.prompt_segments`）：等真实需求出现再加。
- 是否扩展为多 `<context>` 块：观察 LLM 实测表现，必要时再开。
- `prompt_composer=` 旧 2-arg 签名 deprecation timeline：暂不发 deprecation warning，沿用 `_LegacyCallableRunner` 同思路保留无限期兼容。
