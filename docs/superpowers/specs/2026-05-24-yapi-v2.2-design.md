## 1. 本次设计的动机

v2.1 把 yapi 收拢为 "FastAPI superset + 显式 prompt 入口"。但有一个 v2 留下的设计妥协一直没修：

- 用户函数的 **`return` 值** 被同时承担"函数结果"与"动态 prompt 段"两层语义。返回注解是 `WishOut`（结果模型），实际允许的返回值是 `None | str`（prompt 段）——这是一个内部矛盾，靠类型守卫强行兜住。
- 与此同时，越来越多的应用需要把"结构化的事实片段"（用户档案、近期订单、商品快照……）塞进 system prompt 里。在 v2.1 下，唯一的通道是 `return "string"`，所以用户被迫自己把所有结构 `json.dumps` 成一段字符串再 return。多个段也只能用 `\n\n` 自己拼。

更早期讨论"state 集成"的方向（v1 spec 的 `state_storage=` / `state_dependencies=`、v2.1 草稿期一度考虑的 `Annotated[T, FromState(...)]`）有意没有进入 v2.2。理由有两条：

1. **存储侧抽象的回报太低**。Redis / Mongo / Dynamo / 内存 dict / SQL session 这些客户端用 FastAPI 原生 `Depends(...)` 拿就好，yapi 再造一层 `StateStore` Protocol 只是无用的中间层。
2. **ID 解析 / 依赖关系是业务问题**。每个项目里 ID 怎么算（user_id？session_id？item_id？复合 key？）都不一样，yapi 给一个内置 callable 形态最终只会变成"开发者绕开它写 Depends"。

所以 v2.2 的立场是：**把"往 prompt 里塞结构化片段"这条通道做大，state 这件事（取哪里、查哪里、转什么格式）完全留给开发者**。yapi 在通道上只做两件事：

- 注入一个新对象 `PromptContext`；
- 把它收集到的片段拼到 system prompt 里，外裹一层 `<context>...</context>` XML 边界。

## 2. v2.2 设计原则

继承 v2.1 全部原则，并新增 3 条：

1. **prompt 增量是 side effect，不是 return value**。函数的 `return` 应该承载函数的"结果"语义；prompt 段写入应当走"被注入对象 + 多次调用"的副作用通道（参照 FastAPI `BackgroundTasks` 与 Starlette `Request` 的设计取向）。
2. **yapi 不做存储抽象，但接受结构化输入**。`ctx.add(value)` 接受任意类型，yapi 按内置规则把它转成字符串。开发者不必为了塞 prompt 而手动 `json.dumps`。
3. **prompt 增量必须有 XML 边界**。所有 ctx 内容统一裹一层 `<context>...</context>`，让 LLM 在 system prompt 中明确识别"上下文事实"段与"系统指令 / 文档"段的边界。

## 3. PromptContext：新对外表面

这是 v2.2 唯一的新公开符号。

### 3.1 用户视角

```python
from typing import Annotated
from fastapi import Depends
from pydantic import BaseModel
from yapi import PromptRouter, PromptContext

class WishIn(BaseModel):
    user_id: str
    wish: str
    item_id: str

class WishOut(BaseModel):
    """你是一个愿望受理实体。"""
    granted: bool
    message: str

router = PromptRouter()

@router.prompt.post("/wish")
def make_a_wish(
    req: WishIn,
    store: Annotated[Store, Depends(get_store)],
    ctx: PromptContext,                                  # ← yapi 自动注入
) -> WishOut:
    """根据用户档案决定是否实现愿望。"""
    profile = store.get(f"user:{req.user_id}")
    item    = store.get(f"item:{req.item_id}")

    ctx.add_section("User Profile", profile)
    ctx.add_kv("item_id", req.item_id)
    ctx.add(profile.last_orders)
    # 函数不需要 return；也可以 return "tail" 作为最后一段（语法糖）。
```

### 3.2 PromptContext 表面

公开方法只有三个：

| 方法 | 形态 | 输出片段 |
|---|---|---|
| `ctx.add(value)` | 任意值 | `<value 按 §3.3 转 str>` |
| `ctx.add_kv(key, value)` | 键值对 | `{key}: <value 按 §3.3 转 str>` |
| `ctx.add_section(name, body)` | 命名段 | `# {name}\n<body 按 §3.3 转 str>` |

无 `clear` / `pop` / `extend` / 条件添加方法。`PromptContext` 是纯 append-only 的容器；想做条件添加用 Python 原生 `if` 即可。

PromptContext 还有一个**内部**方法 `segments() -> tuple[str, ...]`，由 `compose_prompt` 调用拿到拼接后片段元组，**不**对外承诺稳定（带下划线前缀的另一个候选是 `_segments`，按 Python 公约表达"内部用"）。本 spec 用 `segments()`，最终实现可保留下划线变体——这不属于对外契约。

### 3.3 `value → str` 转换规则

按顺序匹配：

| 类型 | 转换 |
|---|---|
| `str` | 原样 |
| `BaseModel` 实例 | `value.model_dump_json()` |
| `dict` / `list` / `tuple` | `json.dumps(value, ensure_ascii=False)` |
| 其它 | `str(value)` |

`None` 在 `ctx.add` / `ctx.add_kv` / `ctx.add_section` 任一处出现都装饰期不可检测，请求期抛 `RuntimeExecutionError`（§6）。允许"想塞空段"的用法时用户应显式 `ctx.add("")` 或省略调用。

### 3.4 XML 边界

收集到的所有片段（按 `ctx.add*` 调用顺序 + 末尾追加 `return` 的 str 段，如果有）用 `\n\n` 串联，整体外裹 `<context>...</context>`，作为 system prompt 的最后一段。

**空段省略**：当 PromptContext 没有任何 `add*` 调用，且函数 `return` 不是非空 str 时，`<context>` 段整段不输出（避免空 token 浪费、让 v2.2 路由在"无动态段"场景下 prompt 形态与 v2.1 完全一致）。

完整 system prompt 拼接顺序：

```
DEFAULT_SYSTEM_PREFIX
↓
response_model.__doc__         （如非空）
↓
function.__doc__               （如非空）
↓
<context>                      （仅当至少有一个 segment）
  segment 1
  
  segment 2
  
  ...
</context>
```

段间用 `\n\n` 串联。

### 3.5 一个完整例子的最终 prompt

接 §3.1 的路由，假设 `req.user_id = "u-1"`、`store.get` 返回的 profile 是 `Profile(name="djj", vip=True, last_orders=[...])`：

```
You are the execution engine behind a declarative HTTP endpoint. Return data that strictly matches the required response model.

你是一个愿望受理实体。

根据用户档案决定是否实现愿望。

<context>
# User Profile
{"name":"djj","vip":true,"last_orders":[...]}

item_id: i-1

[{"order_id": "o-1", ...}, {"order_id": "o-2", ...}]
</context>
```

## 4. 实现层架构

### 4.1 新文件 / 改动文件清单

- **新建** `yapi/prompt_context.py`：定义 `PromptContext` 类与 `_format_value` helper。
- **修改** `yapi/__init__.py`：re-export `PromptContext`，加进 `__all__`。
- **修改** `yapi/router.py`：
  - `ParamRole` 新增 `PROMPT_CONTEXT` 值。
  - `_classify_param` 在 `Annotated` 拆解前先检查 `base is PromptContext or (isinstance(base, type) and issubclass(base, PromptContext))`；命中即返回 `PROMPT_CONTEXT`。**拒绝**任何带 FastAPI marker 的 PromptContext 参数（`Annotated[PromptContext, Body()/Query()/Depends()]`）——装饰期 `YapiDeclarationError`。
  - `_introspect` 多返回一项 `ctx_param_name: str | None`。一个路由最多一个 PromptContext 参数；声明两个装饰期报错。
  - `handler` 闭包：仅当 `ctx_param_name` 存在时构造 `ctx = PromptContext()` 并塞进 `kwargs[ctx_param_name]`；调用用户函数；类型守卫 return 仍按 v2.1 仅允许 `None | str`；最后把 `prompt_context=ctx` 与 `dynamic_prompt=returned` 一并传给 `Runtime.execute`。
  - `handler.__signature__`：**过滤掉 ctx 参数**——FastAPI 看到的签名里不能有 `PromptContext`，否则 FastAPI 会试图把它当 query / body 解析并失败。这复用 v2.1 已经在用的"yapi 内部视图 vs FastAPI 视图分离"策略。
- **修改** `yapi/runtime.py`：
  - `Runtime.execute` 新增 keyword 参数 `prompt_context: PromptContext | None = None`，位置参数保持兼容。
  - `compose_prompt` 函数签名变为 `(endpoint, prompt_context, dynamic_prompt) -> str`，按 §3.4 规则拼接并外裹 XML。
  - `prompt_composer` 注入点的兼容适配：若用户传入的 composer 是 v2.1 形态 `(endpoint, dynamic_prompt) -> str`，包一层 adapter（catch 多 keyword 的 `TypeError` 后回退旧调用），与 `_LegacyCallableRunner` 同思路。
- **不变** `yapi/runner.py` / `RunnerContext`：runner 看到的仍只是已经拼装好的 `prompt: str`（包含 `<context>` 段）。YAGNI——见 §10。

### 4.2 ParamRole 与 handler signature 的两套视图

v2.1 已经在做"内部分类 vs FastAPI 看见的签名"两套视图，v2.2 在此基础上再细化：

- `_introspect` 返回的 `param_roles: dict[str, ParamRole]` 是 yapi 内部状态，用于决定 handler 闭包内每个参数往哪去（request_model / injected / ctx）。
- `handler.__signature__` 是 FastAPI 看到的视图，v2.1 已经从原签名直接复用并保留 `Annotated`；v2.2 新增一步：**过滤掉 `PROMPT_CONTEXT` 角色的参数**。

```python
fastapi_visible_params = [
    p for p in original_signature.parameters.values()
    if param_roles.get(p.name) is not ParamRole.PROMPT_CONTEXT
]
handler.__signature__ = inspect.Signature(
    parameters=fastapi_visible_params,
    return_annotation=response_model,
)
```

`handler.__annotations__` 同步剔除 ctx 参数；`return` 注解保持为 `response_model`。

### 4.3 PromptContext 实现骨架

```python
# yapi/prompt_context.py
from __future__ import annotations

import json
from typing import Any

from pydantic import BaseModel

from yapi.errors import RuntimeExecutionError


def _format_value(value: Any) -> str:
    if value is None:
        raise RuntimeExecutionError(
            "PromptContext does not accept None; use an empty string if you want an empty segment."
        )
    if isinstance(value, str):
        return value
    if isinstance(value, BaseModel):
        return value.model_dump_json()
    if isinstance(value, (dict, list, tuple)):
        return json.dumps(value, ensure_ascii=False)
    return str(value)


class PromptContext:
    def __init__(self) -> None:
        self._segments: list[str] = []

    def add(self, value: Any) -> None:
        self._segments.append(_format_value(value))

    def add_kv(self, key: str, value: Any) -> None:
        self._segments.append(f"{key}: {_format_value(value)}")

    def add_section(self, name: str, body: Any) -> None:
        self._segments.append(f"# {name}\n{_format_value(body)}")

    def segments(self) -> tuple[str, ...]:
        return tuple(self._segments)
```

### 4.4 compose_prompt 实现骨架

```python
# yapi/runtime.py (replace existing compose_prompt)
def compose_prompt(
    endpoint: PromptEndpoint,
    prompt_context: PromptContext | None,
    dynamic_prompt: str | None,
) -> str:
    sections = [DEFAULT_SYSTEM_PREFIX]
    if endpoint.response_doc:
        sections.append(endpoint.response_doc)
    if endpoint.function_doc:
        sections.append(endpoint.function_doc)

    ctx_segments = list(prompt_context.segments()) if prompt_context else []
    if dynamic_prompt:
        ctx_segments.append(dynamic_prompt)
    if ctx_segments:
        body = "\n\n".join(ctx_segments)
        sections.append(f"<context>\n{body}\n</context>")

    return "\n\n".join(sections)
```

## 5. 数据流

```
HTTP request
  │
  ▼
FastAPI 按 handler.__signature__（已过滤 ctx 参数）解析：
  - BaseModel 参数 → request body
  - Depends → 解析依赖
  - Annotated[T, Query/Header/Cookie/Path/Form/File] → injected fields
  │
  ▼
handler 闭包（async）：
  ctx = PromptContext() if ctx_param_name else None
  user_kwargs = kwargs ∪ ({ctx_param_name: ctx} if ctx else {})
  returned = await/sync user_func(**user_kwargs)
  
  if returned is not None and not isinstance(returned, str):
      raise RuntimeExecutionError(...)
  
  await run_in_threadpool(
      Runtime.execute,
      endpoint=...,
      request_model=req,
      injected=...,
      prompt_context=ctx,
      dynamic_prompt=returned,
  )
  │
  ▼
Runtime.execute:
  prompt = compose_prompt(endpoint, prompt_context, dynamic_prompt)
  # prompt 含 <context>...</context> 段（如非空）
  runner_ctx = RunnerContext(prompt=prompt, request=..., injected=..., path=..., method=...)
  payload = runner.run(runner_ctx)
  return response_model.model_validate(payload)
```

**不变量**：

1. `PromptContext` 实例严格请求局部。每次请求新建，不跨请求、不共享。
2. `ctx.add*` 是纯追加，无 mutation API；段序与调用序一致。
3. `ctx` 在 `_introspect` 期就被识别并从 `handler.__signature__` 抹掉，FastAPI 永远不会试图把它当 query / body 解析。
4. `Depends` 拿到的对象（如 `store`）跟 v2.1 一致进入 `injected` dict，runner 仍能看到。
5. `Runtime.execute` 的对外签名向后兼容（仅追加 keyword 参数）；`RunnerContext` 字段集合**不变**。

## 6. 错误目录

| 触发条件 | 时机 | 错误类型 | 错误消息 |
|---|---|---|---|
| 同一路由声明两个 `PromptContext` 参数 | 装饰期 | `YapiDeclarationError` | `"yapi prompt route '{name}' may declare at most one PromptContext parameter"` |
| `PromptContext` 参数带 FastAPI marker（`Annotated[PromptContext, Body()/Query()/Depends()/...]`） | 装饰期 | `YapiDeclarationError` | `"yapi prompt route '{name}' parameter '{p}': PromptContext is auto-injected by yapi and must not carry FastAPI markers"` |
| `ctx.add(None)` / `ctx.add_kv(k, None)` / `ctx.add_section(name, None)` | 请求期（用户函数体内） | `RuntimeExecutionError`（由 `_format_value` 抛出） | `"PromptContext does not accept None; use an empty string if you want an empty segment."` |
| 用户函数 return 非 None 非 str | 请求期 | `RuntimeExecutionError`（v2.1 已有） | unchanged |
| `prompt_composer` 旧签名调用失败 | 请求期 | adapter 自动转换 | adapter 内部 catch 旧签名 `TypeError` 后切换调用方式；最终用户不可见 |

**关于 ctx.add(None) 抛错的时机**：`_format_value` 在用户代码内被同步调用，因此 `RuntimeExecutionError` 会从用户函数体内冒出来，**沿用** v2.1 路径——直接向上冒到 FastAPI 默认 500 处理，不经 `Runtime.execute` 包装层。这与 v2.1 "动态 prompt 计算发生在 Runtime.execute 之前的 handler 层"的设计立场一致。

## 9. 迁移与兼容性

### 9.1 兼容部分

- `from yapi import PromptRouter`：**不变**。
- `from yapi import AgentRunner, RunnerContext, YapiError, YapiDeclarationError, RuntimeExecutionError, YapiUsageWarning`：**不变**。
- 所有 v2.1 路由的源码：**无需修改即可工作**。`return None` 与 `return "str"` 仍合法；不写 ctx 参数的路由按 v2.1 路径处理。
- `agent_runner=lambda **_: {...}` 风格注入：**仍然能用**。
- `Runtime.execute` 的对外签名：兼容（仅追加 keyword 参数）。
- `compose_prompt` 的对外形态：源码内部签名变化，但作为公开扩展点 `prompt_composer=` 注入的旧形态 callable 通过 adapter 自动兼容。
- `RunnerContext` 字段集合：**不变**。

### 9.2 破坏部分

仅一处 user-visible 行为变化：

| 破坏点 | v2.1 行为 | v2.2 行为 | 迁移 |
|---|---|---|---|
| 路由内 `return "hint"` 在 system prompt 中的形态 | system prompt 末尾追加 `\n\nhint` | system prompt 末尾追加 `\n\n<context>\nhint\n</context>` | 通常无需迁移（多数 prompt 对 XML 边界鲁棒）；若用户 prompt 中含字面"看 prompt 末尾的一段话"这种位置依赖措辞，需重述为"看 `<context>` 标签内的内容" |

### 9.3 版本号

## 10. 明确不做的事

- **不**实现内置 StateStore Protocol / 抽象 KV 接口 / `Annotated[T, FromState(...)]` marker / 装饰器 `state=` 参数。state 这件事 yapi 不集成，留给开发者用 FastAPI 原生 `Depends` + 任意客户端解决。
- **不**为 `RunnerContext` 增加 `prompt_segments` 字段。runner 看到的仍是已经拼装好的 `prompt: str`；需要 segment 级粒度的 runner 自己 parse `<context>` 段（按 YAGNI 原则推迟到 v2.3 或更晚）。
- **不**允许 `ctx.add(None)`。`None` 在 prompt 里没有合理语义，拒绝比静默跳过更显性。
- **不**为 `PromptContext` 加 `clear` / `pop` / `extend` / 条件添加 helper。append-only 是有意为之；想跳过用 Python 原生 `if` 写。
- **不**支持多个 `<context>` 块（如 `<user_context>` / `<item_context>` 分离）。一个路由一个 `<context>`，里面用 `add_section(name, ...)` 区分子段。
- **不**允许用户自定义外裹 tag。`<context>` 是固定字面量；想换标签的开发者注入 `prompt_composer=` 自己拼。
- **不**对 v2.1 老路由（`return str`）静默改语义而不外裹 XML——一致性比兼容性优先（§9.2）。
- **不**在 v2.2 落实 CI lint / format / mypy 强校验（沿用 v2.1 §10 立场，独立 PR）。
- **不**在 v2.2 写 CHANGELOG / CONTRIBUTING 内的新章节迁移指南（README + release notes 自动化已足）。

## 11. 一句话总结

`yapi` v2.2 把"塞给 LLM 看的 prompt 增量"从 `return str` 的副作用通道升级为**显式注入的 `PromptContext` 对象**：开发者 `ctx.add(任意值)` 多次追加，yapi 按内置规则转字符串、外裹 `<context>...</context>` XML 边界、拼到 system prompt 末尾；state 这件事 yapi 不集成，存储客户端继续用 FastAPI 原生 `Depends` 解决，开发者用 `ctx.add_section / add_kv / add` 决定哪些事实进 prompt。
